- **ADR-022** 2026-09-15 — PR #3 (M0.5) went through a 4-angle adversarial review before merge (silent-failure, type-design, test-coverage, general-adversarial — same practice as M0's, ADR-010/014-019) that found and fixed real defects, not style nits: (1) `appName` and `angularCliVersion` in `scaffoldTargetWorkspace` were passed into `spawn`'s argv completely unvalidated. Confirmed exploitable, not theoretical — an `appName` starting with `-` is parsed by `ng new` as a flag rather than a name, and an `angularCliVersion` like `npm:cowsay@1.6.0` exploits npm's `name@npm:other-package@version` alias syntax to make `npx --yes @angular/cli@<version>` install and run an arbitrary package under the `@angular/cli` name. Fixed with a `validateScaffoldOptions` pre-check (`appName` must match `^[a-z][a-z0-9-]*$`, `angularCliVersion` must be exact `major.minor.patch`, `outputDir` must be absolute) run before any filesystem or subprocess work. Both inputs are operator-supplied today, but `PLAN-m0.5-scaffold.md`'s own Open Questions already contemplates a future caller deriving `appName` from the source repo's `package.json` — the exact change that would turn this into injection from untrusted input, which is why it's fixed now rather than deferred. (2) `run-command.ts`'s timeout only sent SIGTERM to the immediate `npx` process, never to grandchildren (`npm install` inside `ng new`) — a child that ignored SIGTERM, or a detached grandchild, could hang the promise forever, the exact failure the function's docstring claimed was impossible. Fixed: spawn detached on POSIX so the child becomes a process-group leader, kill the whole group via `process.kill(-pid, signal)` (falling back to a direct kill if that fails or on Windows), and escalate from SIGTERM to SIGKILL after a 5s grace period if the tree hasn't exited. (3) `isEmptyOrMissing` in `scaffold-workspace.ts` treated *any* `readdir` failure — not just "doesn't exist" — as "safe to scaffold into," including permission errors and "outputDir is actually a file," silently disabling the non-empty-directory guard exactly when the directory couldn't be inspected. Fixed to only treat `ENOENT` as "missing" and propagate everything else as a proper `ScaffoldResult` failure (added a `failureResult` helper, used at every early-return, so this and the previously-unguarded `mkdir(parentDir, {recursive:true})` — which could reject and break the module's "never throws" contract — both resolve instead of rejecting). Verified after the fixes: real, unmocked `scaffoldTargetWorkspace` + `verifyWorkspaceBuilds` run against a scratch directory (workspace generated, `ng build` exit 0), plus a real CLI run confirming both injection payloads above are now rejected before any subprocess spawns. 99/99 unit tests passing (8 new), typecheck and lint clean — superseded-by: none

This is exactly the silent no-op CLAUDE.md's reporting-honesty rule forbids, confirmed independently by three review angles. Fixed by adding `warnings?: readonly string[]` to `CodemodResult`'s `matched: true` variant, and having the CLI print them even on a successful run. (2) **Two registrations sharing the same name in one file produced two identically-named `class` declarations** — a real SyntaxError, silently emitted as `matched: true`. Fixed: the second occurrence of a class name already used earlier in the same file is now a documented skip. (3) **`CodemodResult` was an optional-field bag, not a discriminated union** — `{matched: true}` with no `output` type-checked cleanly, and `cli.ts` had already band-aided around it (`result.output ?? ''`), which would have silently written an empty file instead of the type ruling the state out. Fixed: `CodemodResult` is now `{matched: true; output: string; warnings?: readonly string[]} | {matched: false; reason: string}`. (4) **A `--out` path identical to the input file silently overwrote the source**, contradicting the command's own printed description ("Never writes back to the source repo"). Fixed with an explicit resolved-path equality guard, refused with exit code 1. (5) **A DI function with a destructured, default-valued, or rest parameter was either silently mistranslated or produced invalid TypeScript** — `function ({ $scope }) {}` doesn't throw when read via `Parameter#getName()`, it returns the pattern's own source text (`"{ $scope }"`), which then got spliced straight into a constructor parameter, producing `constructor(private { $scope }: any)` — invalid TS (a parameter property can't use a binding pattern), confirmed via real compiler diagnostics, not assumed. A default-valued parameter (`$scope = null`) passed the existing dependency/param-count check but silently dropped the default with no signal at all. Confirmed by actually running the codemod against a constructed IIFE fixture, not just reasoning about it — the emitted class referenced `helper` from a scope it was no longer inside. Fixed: the walk now also stops at the nearest enclosing `Block`, not only the `SourceFile`. (2) **A registration name colliding with a pre-existing top-level binding (a `function`, `class`, or `var`/`let`/`const` already in the file) still produced two conflicting declarations** — ADR-025's duplicate-name fix only tracked names this codemod itself had already emitted in the same run, not names the file already had before the codemod touched it. - **ADR-027** 2026-09-15 — Pattern #1 ($scope.x = y → class property, `docs/product-spec.md §6.3`) is scoped to bare-function-DI `.controller` registrations only — array-style DI is pattern #3's job (the two are kept deliberately non-overlapping, so a run's mechanical-hit-rate numbers never double-count the same registration), and `.service`/`.factory` are excluded since `$scope` is a controller/directive-link concept, not something services are conventionally injected with. The shared class-wrapping plumbing pattern #3 built (IIFE-safe insertion point, identifier/reserved-word validation, pre-existing-binding check, simple-parameter check, position-grouped edit application) was extracted into `libs/migration-core/src/codemods/class-wrapping.ts` and reused rather than re-derived, per the M1 session-log entry's own instruction to do exactly that — `array-di-to-constructor.ts`'s existing test suite passing unmodified after the extraction confirms it's a pure refactor, not a behavior change. Only `$scope.<name> = <value>` — a single property level deep, matching the pattern's literal definition — is rewritten; a `$scope.$watch(...)`/`$scope.$on(...)` method call, a compound-assignment operator (`+=` etc.), or a deeper chain (`$scope.a.b = y`) is left untouched. **A real bug was caught by actually running the codemod against a realistic file before this even reached adversarial review** (CLAUDE.md's "actually run it" rule doing its job): a `$scope.x = y` assignment inside a nested *non-arrow* function (e.g. `$http.get(...).then(function (res) { $scope.x = res.data; })`) was rewritten to `this.x = res.data`, but a plain function rebinds `this` based on how it's called, not lexically the way `$scope` closure-captures correctly — so `this` there would not have referred to the class instance at all. An arrow function doesn't have this problem (`this` stays lexical), so nesting inside one is safe unless it *also* redeclares its own `$scope` parameter (a second, independent way a nested function can invalidate the rewrite — e.g. a `$watch` callback's `function (newVal, oldVal, $scope) {...}` third argument, a genuinely different binding). Fixed: any `$scope` assignment inside a nested non-arrow function, or inside a nested function of either kind that shadows `$scope` as its own parameter, is a documented whole-registration skip — superseded-by: ADR-028
- **ADR-028** 2026-09-15 — PR #8 (pattern #1) went through the same two-round adversarial review practice as PR #6 (ADR-025/ADR-026) — silent-failure, type-design, test-coverage, and an independent 8-sub-agent general review, all run before merge. Round 1 (this PR's own description) claimed shadowing was fully handled; round 2 found three separate real gaps in that claim, all confirmed by actually running the codemod, not just read: (1) **`isUnsafeNestedAssignment`'s shadow check only inspected a nested function's *parameters*, never a local `var`/`let`/`const $scope` declared inside one** — `function ($scope) { $scope.refresh = function () { var $scope = fetchSnapshot(); $scope.loaded = true; }; }` was confirmed to silently rewrite the inner (shadowed) assignment to `this.loaded = true`, which would have set a property on the class instance instead of on `fetchSnapshot()`'s result. Root-caused, not patched: hand-rolled ancestor-walking to detect "is this identifier shadowed" is exactly the kind of scope-resolution problem the TS compiler's binder already solves correctly for every shadowing shape at once (parameter, `var`, `let`, `const`, `catch` clause, ...) — three independent review agents finding three different holes in the same hand-rolled check was itself the signal to stop patching cases one at a time. Fixed by switching to `Identifier#getSymbol()?.getDeclarations()` and comparing the resolved declaration node to the controller's own `$scope` parameter by reference — confirmed empirically first (a scratch script showing ts-morph correctly resolves the outer vs. shadowed `$scope` to different declaration nodes) before rewriting the production check. This also **simplified** the design: a shadowed assignment is now simply excluded from the candidate set (it genuinely isn't this pattern's target) rather than triggering a whole-registration skip, so an outer, unshadowed `$scope.x = y` in the same function now correctly still transforms even when a *different*, shadowed occurrence exists elsewhere in the body. (2) **Mid-function reassignment of the bare `$scope` identifier itself** (`$scope = $scope.$new();`) was undetected — binding resolution alone can't catch this, since reassignment doesn't change which declaration an identifier resolves to, only its runtime value, so every later `$scope.x = y` would still resolve to the same parameter and pass the (now-correct) shadow check while actually mutating whatever `$scope` currently holds. Fixed with a separate, explicit check: any bare-identifier assignment to `$scope` (resolving to the same parameter) anywhere in the function is a documented whole-registration skip. (3) **The nested-function "`this` rebinds" boundary check omitted `GetAccessorDeclaration`/`SetAccessorDeclaration`** — a getter/setter's `this` is call-site-bound exactly like a plain function's, not lexical, but wasn't in the enumerated node-kind list. Confirmed via execution: a `$scope.x = 1` inside `{ get foo() { $scope.x = 1; } }` was silently rewritten to `this.x = 1`. Fixed by adding both accessor kinds to the boundary check. **Generalized while fixing, per the "beyond the basics" review directive:** the this-rebinding boundary check (fix 3) was moved out of `scope-assignment-to-class-property.ts` into `class-wrapping.ts` as `isInsideThisRebindingBoundary`, parameterized on the outer function rather than hardcoded to `$scope` — the altitude/conventions review angle correctly flagged that pattern #10 ($emit/$broadcast/$on → RxJS `Subject`, also in the fixed v1 scope) will rewrite free references inside a class-wrapped body and hit the identical hazard; leaving the check pattern-local would mean re-deriving it a second time or shipping without it. Separately, the type-design review's repeat finding (`constructorParamsText` didn't itself enforce the `isSimpleParameter` invariant it depends on, only duplicated caller-side checks did — the same failure shape ADR-025 found for `CodemodResult`) was fixed by making `constructorParamsText` throw if given a non-simple parameter, a safety net behind the existing per-caller check that produces the real skip reason. **Deliberately deferred, not fixed:** both PR #8's review rounds independently flagged that `RawMatch`/`Candidate` interfaces and the collect→sort→validate→build loop structure are now duplicated near-verbatim between `array-di-to-constructor.ts` and `scope-assignment-to-class-property.ts` (differing by ~2 pattern-specific checks and 2 field mappings out of ~25 lines each), and that `class-wrapping.ts`'s own stated purpose is only half-delivered as a result. Not extracted in this PR: with only two patterns built, a generic pipeline abstracted from two data points risks overfitting its shape to exactly those two and needing a rework once pattern #2 or #4 shows a third variation — the "rule of three" tradeoff, not an oversight. Revisit when the next class-wrapping pattern lands and the actual shape of the variation across three implementations is known. Re-verified after all fixes: 19/19 tests in this pattern's spec (6 new — local-var-shadow-transforms-sibling, reassignment skip, accessor skip, computed-property miss, chained-controller ordering, plus the existing shadow test's reason string updated to reflect the new "no match" behavior), full workspace suite green, and all three fixed scenarios (local-var shadow, reassignment, accessor) re-run for real through the actual function before being locked into tests — superseded-by: none

- **ADR-032** 2026-09-16 — A second, independent `/code-review high` pass against ADR-031's own fix (same two-round practice as every other pattern PR, run before merge) found three more real issues, none caught by the first round: (1) **Two `.controller` registrations resolving to the same underlying named `function` declaration corrupted output** — `collectBareFunctionControllerMatches`/`classWrappingSkipReason`'s duplicate check only compares class *names*, not the underlying `fn` node, so `.controller('CtrlA', X).controller('CtrlB', X)` (two different registration names both referencing the same `function X`) produced two candidates, each scheduling deletion of `X`'s identical source span computed against the *original*, pre-edit text. `applyEdits` applies both against the same (by-then-shrunk) string using those stale offsets, corrupting unrelated trailing content — confirmed by actually constructing a file with a marker string after the function and observing it get mangled (`"SHOULD_SURVIVE_UNCHANGED"` → `UNCHANGED"`), not assumed from reading the splice math. Fixed at the root two ways: `collectBareFunctionControllerMatches` now additionally requires the referenced function's own name to equal the registration's string-literal name (`namedFn.getName() === className`) — the confirmed-dominant real-world shape always satisfies this, and a mismatch is a different, unsupported idiom, not something to guess through — and each pattern's own loop now tracks a `claimedNamedDeclarations: Set<Node>`, skipping (with a specific reason) any later match that resolves to a function declaration an earlier match already claimed, as a second, independent safety net.
