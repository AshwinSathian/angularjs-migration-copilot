- **ADR-022** 2026-09-15 — PR #3 (M0.5) went through a 4-angle adversarial review before merge (silent-failure, type-design, test-coverage, general-adversarial — same practice as M0's, ADR-010/014-019) that found and fixed real defects, not style nits: (1) `appName` and `angularCliVersion` in `scaffoldTargetWorkspace` were passed into `spawn`'s argv completely unvalidated. Confirmed exploitable, not theoretical — an `appName` starting with `-` is parsed by `ng new` as a flag rather than a name, and an `angularCliVersion` like `npm:cowsay@1.6.0` exploits npm's `name@npm:other-package@version` alias syntax to make `npx --yes @angular/cli@<version>` install and run an arbitrary package under the `@angular/cli` name. Fixed with a `validateScaffoldOptions` pre-check (`appName` must match `^[a-z][a-z0-9-]*$`, `angularCliVersion` must be exact `major.minor.patch`, `outputDir` must be absolute) run before any filesystem or subprocess work. Both inputs are operator-supplied today, but `PLAN-m0.5-scaffold.md`'s own Open Questions already contemplates a future caller deriving `appName` from the source repo's `package.json` — the exact change that would turn this into injection from untrusted input, which is why it's fixed now rather than deferred. (2) `run-command.ts`'s timeout only sent SIGTERM to the immediate `npx` process, never to grandchildren (`npm install` inside `ng new`) — a child that ignored SIGTERM, or a detached grandchild, could hang the promise forever, the exact failure the function's docstring claimed was impossible. Fixed: spawn detached on POSIX so the child becomes a process-group leader, kill the whole group via `process.kill(-pid, signal)` (falling back to a direct kill if that fails or on Windows), and escalate from SIGTERM to SIGKILL after a 5s grace period if the tree hasn't exited. (3) `isEmptyOrMissing` in `scaffold-workspace.ts` treated *any* `readdir` failure — not just "doesn't exist" — as "safe to scaffold into," including permission errors and "outputDir is actually a file," silently disabling the non-empty-directory guard exactly when the directory couldn't be inspected. Fixed to only treat `ENOENT` as "missing" and propagate everything else as a proper `ScaffoldResult` failure (added a `failureResult` helper, used at every early-return, so this and the previously-unguarded `mkdir(parentDir, {recursive:true})` — which could reject and break the module's "never throws" contract — both resolve instead of rejecting). Verified after the fixes: real, unmocked `scaffoldTargetWorkspace` + `verifyWorkspaceBuilds` run against a scratch directory (workspace generated, `ng build` exit 0), plus a real CLI run confirming both injection payloads above are now rejected before any subprocess spawns. 99/99 unit tests passing (8 new), typecheck and lint clean — superseded-by: none

(2) **Two registrations sharing the same name in one file produced two identically-named `class` declarations** — a real SyntaxError, silently emitted as `matched: true`. (3) **`CodemodResult` was an optional-field bag, not a discriminated union** — `{matched: true}` with no `output` type-checked cleanly, and `cli.ts` had already band-aided around it (`result.output ?? ''`), which would have silently written an empty file instead of the type ruling the state out. Fixed: `CodemodResult` is now `{matched: true; output: string; warnings?: readonly string[]} | {matched: false; reason: string}`. (4) **A `--out` path identical to the input file silently overwrote the source**, contradicting the command's own printed description ("Never writes back to the source repo"). Fixed with an explicit resolved-path equality guard, refused with exit code 1. Fixed: the walk now also stops at the nearest enclosing `Block`, not only the `SourceFile`. (2) **A registration name colliding with a pre-existing top-level binding (a `function`, `class`, or `var`/`let`/`const` already in the file) still produced two conflicting declarations** — ADR-025's duplicate-name fix only tracked names this codemod itself had already emitted in the same run, not names the file already had before the codemod touched it. - **ADR-027** 2026-09-15 — Pattern #1 ($scope.x = y → class property, `docs/product-spec.md §6.3`) is scoped to bare-function-DI `.controller` registrations only — array-style DI is pattern #3's job (the two are kept deliberately non-overlapping, so a run's mechanical-hit-rate numbers never double-count the same registration), and `.service`/`.factory` are excluded since `$scope` is a controller/directive-link concept, not something services are conventionally injected with. The shared class-wrapping plumbing pattern #3 built (IIFE-safe insertion point, identifier/reserved-word validation, pre-existing-binding check, simple-parameter check, position-grouped edit application) was extracted into `libs/migration-core/src/codemods/class-wrapping.ts` and reused rather than re-derived, per the M1 session-log entry's own instruction to do exactly that — `array-di-to-constructor.ts`'s existing test suite passing unmodified after the extraction confirms it's a pure refactor, not a behavior change. Only `$scope.<name> = <value>` — a single property level deep, matching the pattern's literal definition — is rewritten; a `$scope.$watch(...)`/`$scope.$on(...)` method call, a compound-assignment operator (`+=` etc.), or a deeper chain (`$scope.a.b = y`) is left untouched. **A real bug was caught by actually running the codemod against a realistic file before this even reached adversarial review** (CLAUDE.md's "actually run it" rule doing its job): a `$scope.x = y` assignment inside a nested *non-arrow* function (e.g. `$http.get(...).then(function (res) { $scope.x = res.data; })`) was rewritten to `this.x = res.data`, but a plain function rebinds `this` based on how it's called, not lexically the way `$scope` closure-captures correctly — so `this` there would not have referred to the class instance at all. An arrow function doesn't have this problem (`this` stays lexical), so nesting inside one is safe unless it *also* redeclares its own `$scope` parameter (a second, independent way a nested function can invalidate the rewrite — e.g. a `$watch` callback's `function (newVal, oldVal, $scope) {...}` third argument, a genuinely different binding). Fixed: any `$scope` assignment inside a nested non-arrow function, or inside a nested function of either kind that shadows `$scope` as its own parameter, is a documented whole-registration skip — superseded-by: ADR-028
