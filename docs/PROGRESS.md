## Where things stand

**Repo and tooling:** Nx workspace scaffolded (npm, Node 24, TypeScript 6, ESLint 10, Vitest 4 — see `docs/decisions.md` ADR-001–004). CI runs one job (`secrets-scan`, gitleaks) — the rest of the pipeline described in `docs/architecture.md §5` gets added as each milestone lands the tooling it needs (ADR-009). Branch protection on `main` requires a PR and a passing `secrets-scan` check; there is no working direct-push path, by design.

**Built and verified (M0):**

- `libs/migration-core/src/ingest/` — AngularJS version detection, build-tool detection, structural (AST-based) Karma/PhantomJS detection and remediation-generation, and the repo-wide secrets scan.
- `libs/migration-core/src/inventory/` — an AST scanner (ts-morph) covering module declarations, the full `angular.Module` registration surface (controller/directive/component/service/factory/provider/value/constant/filter/decorator/animation) with DI extraction, ngRoute/ui-router routes, `$watch` usage, and vendored-framework-source exclusion.

- `fixtures/angular-phonecat` vendored as a pinned git submodule (commit `ef6f6eb`); its `npm install` and real Karma suite (5/5 specs) have both actually been run on Node 24, not assumed to still work.

Went through an 8-angle adversarial review before merge that found and fixed several real bugs — see `docs/decisions.md` ADR-010 and ADR-014–019, and the "Adversarial review round" section of `docs/milestones/m0-inventory.md` for the specifics (a couple are worth reading even if you skip everything else: a regex-based remediation that could corrupt unrelated code, and a scanner that briefly mistook AngularJS's own framework source for the application being migrated).

**Built and verified (M1, in progress — 3 of 10 patterns):**
- `mrholek/CoreUI-AngularJS` (pinned `ef0c602`) and `akveo/blur-admin` (pinned `7f2596f`) vendored as pinned git submodules under `fixtures/`, same convention as `angular-phonecat`. `npm install` actually run against both on Node 24: `CoreUI-AngularJS` is a no-op (no dependencies); `blur-admin` fails plain `npm install` for two reasons unrelated to this project's own code (`node-sass` native build, a dead upstream bower tag) — `npm install --ignore-scripts` is the confirmed-working command for it. See ADR-023, `fixtures/README.md`.
- `libs/migration-core/src/codemods/` stood up as the shared plumbing for all class-wrapping patterns — a pure string-in/string-out transform contract (`CodemodResult`, a discriminated union) plus `class-wrapping.ts` (IIFE-safe insertion point, identifier/reserved-word validation, pre-existing-binding check, simple-parameter check with its invariant enforced at the one function that needs it, position-grouped edit application, a generalized `isInsideThisRebindingBoundary` check, and — new this session — `classWrappingSkipReason` and `collectBareFunctionControllerMatches`, the name-validity/duplicate/param tail and bare-function-`.controller`-collection logic shared identically across all three patterns). Pattern #3 (array-style DI → constructor injection, ADR-024), pattern #1 (`$scope.x = y` → class property, ADR-027), and pattern #2 (controllerAs → component class, ADR-029) all implemented and wired into the CLI as `codemod <pattern> <file>`.
- **A real, severe detection gap was found and fixed this session, in already-merged pattern #1, not just the new pattern**: `collectBareFunctionControllerMatches` only recognized an inline function literal as a `.controller` call's second argument, but running pattern #2 against the real `blur-admin`/`CoreUI-AngularJS` fixtures (not just hand-written test fixtures) showed the dominant real-world idiom — 66 of 91 real `.controller` calls across both fixtures, 0 using an inline literal — is `.controller('X', X)`, referencing a separately-declared `function X(...) {...}`. Pattern #1 had been matching **zero** real controllers in either fixture since merge. Fixed at the shared root (`resolveNamedFunctionDeclaration`, real symbol resolution, plus a second real bug where TypeScript's JS binder treats the equally-common `Ctrl.$inject = [...]` annotation as a second "declaration" of the same symbol) — see ADR-030.
- **That first fix was itself broken, caught by adversarial review before merge, not assumed correct from matching test substrings**: replacing a named `function X(...)` declaration with `class X {...}` in the same textual position produces a real compile error (`TS2449: Class 'X' used before its declaration`) whenever the `.controller('X', X)` call precedes the declaration — the dominant real ordering in both fixtures — since `function` hoists but `class` doesn't. A second bug in the same fix left the `Ctrl.$inject = [...]` statement dangling, assigning a property TypeScript doesn't recognize on the now-class binding (`TS2339`). Confirmed by actually running `tsc` against the codemod's own output, not by re-reading the splice logic. Both fixed at the same shared root — the class is now inserted before the call's own statement and the original `function` (plus its `$inject` annotation, if present) deleted, rather than replaced in place — see ADR-031. **Re-verified for real after the fix**: real `tsc` runs against the codemod's actual output for both scenarios show zero `TS2449` and zero `TS2339`-on-`$inject` errors; pattern #1 confirmed 4/4 real hits against `CoreUI-AngularJS`'s `.controller`-bearing files (all now compile past the TDZ/`$inject` class of error); pattern #2 confirmed 11 real hits against `blur-admin`.
- Real per-repo mechanical hit counts (not smoothed, CLAUDE.md's reporting-honesty rule): `angular-phonecat` 0/0 `.controller` calls (uses `.component()` exclusively, ADR-010 — nothing for either pattern to miss); `CoreUI-AngularJS` 4/4 files pattern #1, 0/4 pattern #2 (correctly zero — its controllers are `$scope`-based, not controllerAs); `blur-admin` 13/50 pattern #1, 11/50 pattern #2. (These counts measure detection/matching, not full compilation — the pre-existing, already-accepted gap of undeclared class fields for `this.x = y`/`vm.x = y` body assignments, present since pattern #1/#3's original merge, is M2 verification-gate territory per the same precedent as the factory-return-type case, not something these codemods pre-empt.)
- All three patterns went through **two or more** independent rounds of adversarial review before merge (more than M0/M0.5's single-round practice, at explicit request to go beyond the basics) — pattern #3: 8 real defects across both rounds (ADR-025, ADR-026); pattern #1: 4 more, including a shadow-detection bug found via a hand-rolled ancestor-walk that three separate review agents independently found different holes in, which was the signal to switch to ts-morph's actual symbol resolution instead of continuing to patch cases one at a time (ADR-028); pattern #2: the named-reference detection gap found by running against real fixtures (ADR-030), then a code-review pass on that very fix catching the TDZ/`$inject`/duplicated-`isPlainAssignment` bugs above (ADR-031). Worth reading even briefly: pattern #3's round 2 found classes being hoisted out of the extremely common `(function(){...})()` IIFE wrapper; pattern #1's round 2 found that `$scope` shadowed by a nested `var` (not just a nested function parameter) was silently mistransformed; pattern #2's review found that its own first fix for one severe bug (zero real hits) introduced a second one (broken compile output) that passing tests alone didn't catch.
- **A second, independent review pass on ADR-031's own fix (ADR-032) found three more real issues**: two different `.controller` registrations resolving to the same underlying named `function` could each schedule deletion of its span using stale (pre-edit) offsets, corrupting unrelated trailing content — confirmed by constructing a file with a marker string that visibly got mangled. Fixed by requiring the referenced function's own name to match the registration name, plus an independent `claimedNamedDeclarations` dedup as a second safety net. Separately, `hasScopePropertyAssignment` (pattern #2's "already pattern #1's territory" check) didn't apply the same this-rebinding-boundary exclusion pattern #1's own transform uses, so a controller with a safe top-level `this.x = y` and an unrelated nested `$scope.y = z` was silently missed by *both* patterns — confirmed by running both codemods against the same file and seeing both report no match. Fixed. A third, smaller DRY finding (`resolvesToParam`/`resolvesToOneOf` near-duplicated) was unified into a shared `resolvesUniquelyTo`.
- 39 new unit tests across pattern #2's spec plus the named-declaration and review-round-2 regression tests added to pattern #1's spec (real hits, real documented misses — dependency-count mismatch, invalid/reserved/duplicate identifiers, destructured/default/rest parameters, pre-existing-binding collisions, IIFE-scoping, chained-call ordering, `$scope` shadowing via symbol resolution, mid-function reassignment, accessor `this`-binding, computed-property misses, `.controller('X', X)`, `Ctrl.$inject = [...]`, class-declared-before-use ordering, same-function dedup, and the this-rebinding-boundary double-miss). 158 total tests workspace-wide, all passing; `nx run-many -t lint,typecheck,test` clean. Merged via [PR #5](https://github.com/AshwinSathian/angularjs-migration-copilot/pull/5), [PR #6](https://github.com/AshwinSathian/angularjs-migration-copilot/pull/6), [PR #8](https://github.com/AshwinSathian/angularjs-migration-copilot/pull/8), and [PR #10](https://github.com/AshwinSathian/angularjs-migration-copilot/pull/10).

And `collectBareFunctionControllerMatches` now resolves **both** the inline-literal and the `.controller('X', X)` named-declaration shapes (ADR-030) — any new pattern keying off a different registration method (`.service`, `.factory`, `.directive`) will need to re-derive the same named-reference resolution for that method, since `resolveNamedFunctionDeclaration` is currently only wired into the `.controller`-specific collector. Worth checking whether array-style DI (pattern #3, `array-di-to-constructor.ts`) has the same named-reference gap for its last-array-element check (`['$http', SomeIdentifier]` instead of an inline function) — not investigated or fixed this session, flagged here rather than assumed fine.

The remaining 7 patterns are fixed v1 scope (`docs/product-spec.md §6.3`) — don't add an 11th opportunistically. Land each as its own vertical slice (transform + before/after fixture-file unit test + wiring), one PR per pattern, same as patterns #1, #2, and #3. Suggested next: pattern #4 (simple directive → `@Component`/`@Directive`) or pattern #9 (one-way `bindings: { x: '<' }` → `@Input()`).

**Before trusting any pattern's hit-rate number again, actually run it against all three vendored fixture repos, not just its own hand-written test fixtures** — this session's biggest finding (ADR-030) was that pattern #1, merged and "verified" in a prior session, matched zero real controllers in two of three fixtures because its test fixtures only ever exercised the inline-literal shape, never the dominant real-world named-reference one. A pattern's own unit tests passing is not evidence its detection generalizes to real code.

Per CLAUDE.md's scope-discipline and reporting-honesty rules: hit-rate and characterization-eligibility numbers (the latter is M2's job, but keep the per-artifact-type breakdown requirement in mind now since it shapes what metadata each codemod should emit) must never be a single smoothed aggregate — report per-repo and, once M2 exists, per-artifact-type. Each pattern's fixture test should capture a real hit *and* a real miss (something that looks like the pattern but has a documented reason to skip it, e.g. a directive with `transclude` for pattern #4) — both patterns' adversarial review rounds so far have repeatedly found bugs in the "why we skip this" / "does this actually resolve to what I think it does" branches, not the happy path. Budget two real review rounds per pattern, not just one — it's found real, distinct bugs both times, every time, so far.
